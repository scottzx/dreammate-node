# 本地工具检索实测：2026-10-10

当前源码默认 **跨已知节点搜索 + 自动发现已就绪的本地模型服务 + 最多 15 个方法摘要**，摘要预算 12000 字符。同优先级的 Qwen3 候选按健康状态与网关地址稳定选择；没有可见模型时仍返回有界词法结果。在相关候选中优先覆盖 2–3 个工具集，并对同集数量与跨节点同方法副本施加折扣；强相关的第 4 个集仍可保留。Agent 应阅读候选后选方法，再 `inspect(method) → invoke`；检索首位不等于可以直接执行。

当前实现只保留 Qwen3；Gemma 的权重、配置及运行和自动发现支持已移除。下文 Gemma 数字为移除前的历史对照，推理均使用本地权重。

## 第一阶段：本机目录与前 5 测试口径

- 从正在运行的本机网关取得 8 个服务、47 个具体方法，包含文件系统、Git、知识图谱记忆、终端、网页、时间、语音转写与分步思考。
- [tool-search-cases.json](../scripts/tool-search-cases.json) 有 42 条人工请求：38 条正例、4 条本目录不支持的请求，覆盖 37 个不同目标。文件系统和 Git 占比较高；不是生产用户流量。
- 三组均使用同一目录、请求、前 5 结果、默认 6000 字符预算与固定余弦阈值 0.35。模型组是接入实际网关排序器后的结果，包含精确方法名优先、语义候选排序和关键词补充，不是纯模型基准。
- [benchmark-tool-search.ts](../scripts/benchmark-tool-search.ts) 逐次验证语义状态和 manifest 中的实际 `alias@revision`；任何回退或错模型都报错，不把词法结果冒充模型成绩。
- Recall@5 是正例中至少一个标注目标进入前 5 的比例，首位正确率按标注目标统计。它们都不等于业务调用成功率。
- 本次根据失败案例改进排序后，用同一请求集复测；没有独立留出集。结果支持本目录试用，不能作为泛化准确率或线上 SLA。

| 条件 | Recall@5 | 首位正确率 | MRR@5 | 预热查询 P50 / P95 | 平均响应字符 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 加权关键词 | 39.5%（15/38） | 23.7%（9/38） | 0.296 | 2.89 / 3.31 ms | 1037 |
| EmbeddingGemma 2，语义优先 | 97.4%（37/38） | 81.6%（31/38） | 0.890 | 35.82 / 49.04 ms | 1815 |

延迟包括排序和本地查询编码，不包括网关跨设备发现；这组预热查询复用文档向量缓存。首次客户端索引与查询时间为 Gemma 1324 ms、Qwen 3591 ms，但 Qwen 含模型切换加载，Gemma 事先预热，不能作为公平的模型冷启动比较。

目录全部方法契约的紧凑 JSON 为 41986 字符，Qwen 搜索摘要平均 1994 字符，同口径减少约 **95.3%**。这是搜索摘要阶段的字符比较，不是实际 token 用量或完整 MCP 传输字节统计；后续会单独加载所选方法的 Schema。本阶段默认搜索最多 6 条，评测使用 5 条；当前默认已改为最多 15 条。服务浏览和无方法 inspect 同样受分页与字符预算约束，不会在无匹配时自动展开全目录。

## 排序缺口与修复

最初使用词法与语义的 RRF（常数 60）。两个模型 Recall@5 均为 35/38，首位分别为 Gemma 19/38、Qwen 22/38。真实描述存在中英文混合，弱中文词法匹配会压过纯语义的正确目标。

例如打开知识图谱实体：Gemma 的正确 `memory.open_nodes` 余弦为 0.838912，却输给余弦仅 0.628546、同时具有中文关键词匹配的 `asr.transcribe`。Qwen 出现同样问题（0.788377 对 0.377351）。这属于排序问题，不能直接归因于模型。

第一阶段顺序为：完整方法名精确匹配优先；其余超过阈值的候选按实际余弦降序，词法只辅助同分；仅关键词匹配的候选补在后面。当前在该基准顺序之上加入工具集平衡，规则记录在 `search.diversity`。`search.ranking=semantic_then_keywords`，`semantic_score` 为余弦，`score` 为基准排名信号；平衡后的结果不保证余弦严格降序，分数不是置信概率。模型不可用时仍退回有界词法检索。旧 RRF 产物留作对照。

## 真实搜索、契约与调用

[只读验证脚本](../scripts/test-local-tool-search.mjs) 对 6 项真实任务执行搜索；只有首位等于人工标注的安全方法时，才继续精确 inspect 和 invoke，并核对业务输出内容。没有执行错误首位，也没有写业务数据。

| 任务 | Gemma 目标位置 | Qwen 目标位置 | 最终调用验证 |
| --- | ---: | ---: | --- |
| 上海当前时间 | 1 | 1 | 两组均成功 |
| 终端平台与执行器版本 | 1 | 1 | 两组均成功 |
| 离线语音引擎状态 | 1 | 1 | 两组均成功 |
| 文件服务允许目录 | 1 | 1 | 两组均成功 |
| 读取项目 package.json 前三行 | 5 | 1 | Qwen 成功；Gemma 未调用 |
| Git 工作区状态 | 3 | 3 | 两组未调用，首位为未暂存差异 |

因此 Gemma 首位选对并验证调用 4/6，Qwen 5/6；实际执行的 9 次调用全部验证通过，两组的 6 个目标均进入前 5。文件读取核对允许目录内公开包名，Git 预检使用服务明确允许的仓库根；未扩大目录权限。另一次后端预检直接调用人工标注方法，6/6 成功，该结果只说明后端可调用，不能算自动检索成功。

Qwen 在 38 条检索正例中剩余 4 个首位误选涉及后台 job 状态、Git 状态与差异、通用 diff 与未暂存 diff、commit 与 add。这些近似方法需要 Agent 阅读摘要、明确操作意图后选择。特别是任务不支持时，当前三组的 4 个负例都返回了候选：**尚无可靠的任务拒识能力**，不能仅按最高分自动执行。

## 第二阶段：跨节点、15 条与工具集平衡

默认搜索范围改为 `all`，最多 15 条、12000 字符；浏览与无方法 inspect 仍默认 10 条、6000 字符。完整方法名精确匹配保持首位，显式 `service_id` 保持单集。在其余查询中先保护前 3 种不同动作，再为最多 3 个相关工具集补充代表项；同集数量与同方法跨节点副本扣分，强相关的其他集仍可进入。分组使用 `service_id`，同集部署到多个节点仍算一个集。

语义组代表需在最高余弦值 0.10 以内；词法模式需至少达到最高关键词分数的 65%。每个工具集由其最佳方法参与比较，不累加整集方法分数。关键词在每个字段中去重计分，描述最多索引 480 字符。这是本次启发式配置，不能保证描述关键词堆砌永远无效，也不是相关性分类器。`search.diversity.relevant_services` 记录最多 3 个优先代表组，不等于结果中的全部服务。

真实拓扑包含 13 个已知节点，扫描其中 9 个在线或本机节点：4 个网关可达、5 个失败，跳过 4 个离线节点。取得 24 个服务实例、14 个不同 `service_id`、219 张节点方法卡，去除节点副本后为 135 种服务/方法组合。其中 40 张只有 capability 名称，没有完整方法描述。本次结果标记 `partial: true`，不能声称覆盖了所有已知节点的工具。

在这份跨节点目录上复用原来的 42 条人工请求，38 个正例仍以原本机目录的目标为标签，没有给新增远端工具补充准确率标签。结果为：

| 条件 | Recall@5 | Recall@15 | 首位正确率 | 缓存后排序与编码 P50 / P95 | 平均响应字符 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 加权关键词 | 34.2%（13/38） | 47.4%（18/38） | 26.3%（10/38） | 16.99 / 18.40 ms | 4481 |
| EmbeddingGemma 2 | 97.4%（37/38） | 97.4%（37/38） | 81.6%（31/38） | 50.86 / 60.68 ms | 5262 |
| Qwen3 | 100%（38/38） | 100%（38/38） | 89.5%（34/38） | 69.90 / 102.41 ms | 5378 |

这张表不含实时网关扫描。在实际搜索入口中，失败节点的 3 秒扫描截止时间使缓存后的跨节点查询约需 3.4 秒。模型只监听本机回环，但工具目录确实来自多个节点；通过异地内网地址调用模型的部署方式已写入指南，未在远端部署常驻模型服务。

另测 3 条人工组合任务及 localhost、单服务过滤，共 5 项范围/预算/模型版本检查全部通过。组合任务分别返回 2、6、9 类服务，来自 2、3、3 个节点；2–3 是优先覆盖目标，并非硬限制。组合请求没有逐意图准确率标签：读取文件/Git/记忆的任务未返回记忆工具，设备状态任务混入 CRM ping，不能将这些检查算作任务完成成功。4 个无支持任务仍会返回候选。

初次网络复测中，同方法副本把 `git_status` 挤到第 6 位；将副本首项扣分从 0.08 调为 0.12（累计上限 0.20）后，整组 Qwen Recall@5 从 37/38 恢复为 38/38，首位正确率未变化。该请求参与了调整，仍无独立留出集。副本保留在完整排序中，分页测试验证 1/5/15 条分页顺序一致、54 张节点方法卡不重复不遗漏。

单机 47 方法目录在新的 15 条设置下，Qwen 仍为 38/38@5、34/38 首位正确，Gemma 37/38@5、31/38 首位正确。Qwen 摘要平均 5488 字符，相对第一阶段同一份完整方法契约 41986 字符少约 86.9%；扩大候选数带来了明确的上下文成本。

## 默认 5 秒：本机与跨节点缓存

第一阶段另起全新离线适配器，先只加载选定模型，使该模型文档缓存为空，然后分别启动 3 个全新 CLI 进程，清除语义超时环境变量以验证真实默认 5000 ms。测量包括 CLI 启动、服务发现、索引和查询；没有执行业务方法。

| 模型 | 首次工具索引 + CLI 查询 | 后两次全新 CLI | 语义状态 |
| --- | ---: | ---: | --- |
| Gemma | 1352 ms | 190 / 192 ms | 3/3 ok |
| Qwen | 2343 ms | 199 / 199 ms | 3/3 ok |

Node 进程缓存最多 4096 条、TTL 5 分钟；本地适配器另有跨 CLI 进程复用的文档 LRU 缓存，最多 4096 条，使用模型版本和工具卡文本哈希隔离。适配器重启后需要重新索引。未预载的模型首次加载可能超出默认预算；应在接收搜索前预热常驻的单个模型。CPU 或其他设备性能尚未实测。

第二阶段另起全新适配器，只预载 Qwen 权重、文档缓存为空，连续启动 3 个新的 CLI；保留默认跨节点/15 条/12000 字符和真实 5000ms 语义预算。第 1 次总耗时 8304ms，语义超时后返回有界词法结果；第 2 次利用适配器已编码文档继续，7575ms、语义成功；第 3 次 3525ms、语义成功。三次均扫描 219 张卡片、返回 15 条并保留网络不完整标记。由此可见，47 方法的本机冷启动成绩不能直接外推到全网；部署时应使用较长预算预建工具文档缓存，步骤见本地模型指南。

## 第三阶段：模型登记、自动发现与故障切换

新增启动器只运行预先准备的本地权重：固定模型实例、真实编码预热、检查所属子进程 PID 后，向本机 node-agent 登记模型 alias、revision、维度、encoding 和 priority，每 15 秒刷新，退出时注销。搜索从扫描到的服务中自动发现候选，直接请求模型所在节点的网关；该网关只代理本机回环模型端口。未配置模型 URL 的客户端无需加载权重。

[生命周期验证脚本](../scripts/test-embedding-discovery.mjs) 使用本机现有 8 服务／47 方法的脱敏目录，启动临时内存网关和一个真实 Qwen worker，保留原有运行网关。7 项检查全部通过：

| 场景 | 实测结果 | 耗时 |
| --- | --- | ---: |
| 未启动模型服务 | `no_provider`，有界词法结果 | 43 ms |
| 模型登记后首次检索 | 无显式模型 URL，自动 Qwen；15 条，`memory.open_nodes` 首位 | 2383 ms |
| 文档缓存就绪，默认预算 | 自动 Qwen，15 条 | 57 ms |
| 默认 `all` 与导入目录 | 保留缓存目录范围诊断，自动发现成功 | 58 ms |
| 指定 `service_id=memory` | 模型服务仍可发现，只返回 memory 方法 | 52 ms |
| 高优先级候选故障 | 首候选 HTTP 502，自动备用真实 Qwen，15 条 | 59 ms |
| 模型正常停止 | 注销成功，恢复 `no_provider` 有界词法结果 | 5 ms |

该次模型版本为 `qwen3@97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3`，返回 1024 维、`dreammate.tool-search.v1:fp32:max512:dim1024`。通过网关单独检查了编码响应维度。冷目录检索使用 60000 ms 预算建立缓存，其余语义搜索使用默认 5000 ms；以上耗时不包含 Python 权重加载。无模型时，同一改写请求的关键词结果仅为 `asr.transcribe`，表明降级保障可用性与上下文上限，不能保持语义召回质量。

这次是真实本地模型与网关链路验证，不是两个物理设备的模型部署。故障主候选由临时登记的未监听端口模拟；默认 `all` 使用仅含临时网关的导入目录，没有重新扫描整个实时网络，也没有调用业务方法。测试结束后，临时网关、注册和所属模型进程均已清理。

新增契约测试另覆盖私网远端模型节点的 MCP 自动路由、`localhost` 范围、业务服务过滤、部分节点失败、两个候选共用截止时间、最多两次尝试、显式 URL 优先，以及 query/document 批次失败、模型版本／维度／encoding 不一致时拒绝并重算备用向量。版本或编码配置改变会隔离客户端缓存。最终 Node 测试 **166/166**、Python 契约测试 **14/14**，类型检查、构建及打包文件检查通过；启动器已纳入 npm 打包清单。该阶段完成时尚未部署到现有网关或发布。

## 复现与本地产物

从源码 checkout 使用已安装开发依赖运行；准备与运行步骤见 [local-embeddings.md](local-embeddings.md)。

```sh
python3 scripts/local-embeddings/prepare.py
node scripts/test-local-tool-search.mjs --phase preflight
node scripts/test-local-tool-search.mjs --phase models
node scripts/test-local-tool-search.mjs --phase models --cold-only
```

综合脚本默认连接 `127.0.0.1:36908`，模型适配器端口为 `8766`；只启动和停止自身的测试适配器，模型阶段会验证实际 manifest 标签。当前使用 `--models qwen3` 复测；Gemma 历史对照不再由当前运行时复现。

本地忽略目录 `.local/tool-search/` 保存：

- `current-services-live.json`：脱敏后的实际目录。
- `gateway-benchmark-live.json`、`routing-models.json`：最终检索与调用结果。
- `gateway-benchmark-rrf.json`、`routing-rrf.json`：修复前结果。
- `routing-preflight.json`：单独的后端可调用预检。
- `default-cold-cli.json`：全新适配器与全新 CLI 的默认超时验证。
- `network-discovery.json`、`network-services-live.json`：跨节点扫描证据与脱敏工具目录。
- `network-search-live.json`：默认范围、预算、真实模型及显式过滤检查，不代表组合任务正确率。
- `gateway-benchmark-diverse-local*.json`、`gateway-benchmark-diverse-network.json`：15 条与工具集平衡后的两模型实测；`*-initial.json` 保留副本权重调整前的对照。
- `default-network-cold-cli.json`：全网空文档缓存下的默认超时、降级和后续恢复。
- `provider-discovery-live.json`：临时网关上的真实模型登记、自动发现、模拟主候选故障与退出降级；不代表双物理节点部署。
- `manifest.json`、`requirements.resolved.txt`、`self-test.log`：版本、真实编码与离线自检证据。
