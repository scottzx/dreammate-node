# MCP 中转：信任与密码学结论

> 日期：2026-11-13
> 范围：公网中转上的鉴权、加密，以及「中转运营方能不能看见明文」。
> 不包含实现。P2 数据面和 P3 控制面另见《MCP-中转三层改造设计》。
> 进度：信任问题没有解决，自建中转暂停。停在 cloudflared Quick Tunnel 能临时打开公网 MCP。隧道域名不固定，进程退出即失效。

## 1. 结论

在现有 MCP 客户端上，中转方只能承诺「不保留」，不能向用户证明自己没看过、没存过。

长连接上的 `wss://` 只防线路上的旁人。中转若是这条 TLS 的终点，隧道里的 HTTP 到它手里就是明文。远端 Agent 那一侧也一样：客户端配置里没有证书指纹字段，中转可以自己申请一张同名证书，把 HTTPS 解开再转发。

因此工具名、参数和返回值至少会在中转进程里出现一次。不写盘、不进日志、不交给别人，是服务器上的软件怎么写的，外面的人核对不了。

要达到「中转在技术上不可能看见」，必须同时满足两件事：私钥只在用户本机，并且客户端钉死这把公钥。第二件现有客户端做不到。在那之前，产品话术只能是运营承诺。

Agent 自己必须看见明文，否则它没法调工具。要拿掉的是对中转运营方的内容信任，不是对 Agent 的信任。

## 2. 两把钥匙

中转要做两道鉴权，而且必须是两把不同的钥匙。客户端那把不能拿来注册长连接，长连接那把也不能拿来调 MCP。

| | 长连接 | 客户端访问 |
|---|---|---|
| 证明什么 | 这台设备可以占这个名字 | 这个调用方可以打这台设备的 MCP |
| 谁拿着明文 | 只有这台设备 | 设备和被授权的 Agent |
| 中转存什么 | 隧道口令的哈希 | MCP api-key 的哈希 |
| 失败时 | 不建立连接 | `401`，不把请求送进长连接 |
| 本机还验吗 | 不验这把 | 再验一次，本机说了才算 |

设备名以中转表里的登记为准，不能由连上来的一方自己挑一个路径占住。同一台设备新连上来，就替换旧连接。

`dmk_` 公网 token 不在这条 MCP 路上。它管的是本机网关 `36908` 的准入。`dreammate_access`、`local_only`、`sharing: local` 仍由本机决定，中转不看工具名。

## 3. 客户端不会做第二层解密

标准 MCP 客户端只会做普通 HTTPS。配置里填 `https://…/mcp` 和 `Authorization: Bearer <MCP api-key>` 就结束了。没有第二层密文，也没有地方填私钥。

因此 P2 若要在中转上预检 Bearer，就得由中转终结 TLS。中转能看见 HTTP 正文，这是预检的代价，不是附带能力。

两条 TLS 是分开的：

```text
远端 Agent  --HTTPS-->  中转（解开 TLS）  --WSS-->  本机 8787
             证书在中转                  隧道口令不进 MCP 配置
```

客户端只校验中转的证书。中转被看光，也拿不到隧道口令的明文，冒充不了这台设备。本机收到转发后，再验一次同一把 MCP api-key。

## 4. 怎样才算中转看不见明文

TLS 必须在远端 Agent 和用户本机之间结束。中转只看 TLS 握手里的域名，把整条连接接到对应设备的长连接上，不终结 TLS。

```text
远端 Agent
  用本机这把公钥做 TLS
        │  密文
        ▼
  中转只认域名，字节原样转走
        │  仍是密文
        ▼
  本机用私钥解开，再进入 127.0.0.1:8787
```

本机生成密钥，私钥不出设备。客户端配置里除了 URL，还要有这把公钥的指纹。证书对不上这把钥匙就拒绝。中转另签的证书会被拒绝。

只校验「这个域名有一张公信 CA 的证书」不够。域名指向中转的 IP 时，占着这个 IP 的人可以自己完成 HTTP-01，再申请一张同名证书，然后解密。这就是信任漏洞。多信一张私有根证书也堵不上：系统里的公信 CA 仍然有效。

这种接法下，中转仍然看得到谁在连、域名、时间和流量大小。看不到工具名、参数、文件内容和返回值，因此也不能做 Bearer 预检和工具级审计。错误令牌会占一条连接，再由本机拒绝。

## 5. MCP 客户端没有指纹字段

MCP 协议和现在这几家常用客户端的配置里，都没有指纹这一项。直接 `mcp add` 一个 `https://` 地址，只能交给系统的 CA 信任库去验证书。

[MCP Transports（2025-11-25）](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) 规定的 Streamable HTTP，是地址、`Authorization` 这类请求头，以及 `Accept`、`Origin`。没有证书指纹、公钥摘要或 pin。

| 客户端 | 远程 MCP 能配的 | 指纹 |
|---|---|---|
| Claude Code | `type`、`url`、`headers` | 无。见 [Claude Code MCP](https://code.claude.com/docs/en/mcp) |
| Cursor | `url`、`headers` | 无 |
| 本机 DSH 连接器 | URL、Bearer、自定义头 | 无 |
| `mcp-remote` | 地址、`--header`，外加 `NODE_EXTRA_CA_CERTS` | 无。只能多信一张自己的根证书 |

`NODE_EXTRA_CA_CERTS` 和「只认这一把公钥」不是一回事。要钉指纹，只能在 Agent 外面加一层自己的程序：它先核对公钥，再把解开的 MCP 交给 Agent。这一层不是 MCP 协议的一部分，现有客户端也不会自动去做。

## 6. 对产品话术的约束

- 自建中转、机器属于用户自己时，内容信任可以先不付。用户信任的是自己的机器。数据面仍可以按「只按域名转发整条 TLS」来做，以后换成别人运营的中转时不用改隧道。
- 我们替别人运营中转时，不能说「技术上不可能看见」。能说的是：转发时会碰到明文；我们承诺不记录工具参数和结果。这是运营承诺。
- 在客户端能够钉指纹之前，不要把「端到端、中转不可见」写进对外说明。
